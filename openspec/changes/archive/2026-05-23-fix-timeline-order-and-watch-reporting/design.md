## Context

手机端每日活动时间线已经从标记事件推导时间段，并在主视图展示给用户回顾当天活动。现有规格要求“按一天发生顺序展示”，但实际使用中用户更关注最近发生的时间段，因此展示层需要改为最近的排在最上面，同时不改变底层时间段推导所需的时间戳顺序。

手表端快捷捕获依赖用户通过 Watch7 Home 键双击打开应用来创建标记。如果一次捕获完成后应用仍保持在前台或捕获会话未结束，后续双击可能不会形成新的启动触发，导致标记上报不再发生。用户确认采用“结束本次捕获会话，保证下次双击可再次触发”的方向，而不是把实现绑定为必须强制后台。

## Goals / Non-Goals

**Goals:**
- 手机端时间线列表按开始时间从近到远展示，最近时间段在列表顶部。
- 时间段推导、标签关联和开放式当前时间段仍基于真实时间戳顺序计算。
- 手表端每次快捷捕获完成后结束当前捕获会话，使下一次 Home 键双击可以再次触发新的标记上报。
- 保留同一次触发生命周期重建时的去重保护，避免一次快捷触发创建多个标记。

**Non-Goals:**
- 不改变标记事件数据模型、同步协议或标签数据模型。
- 不新增手表端标签选择流程。
- 不要求实现某个特定的 watchOS 退后台 API；只要求达到连续快捷触发可用的行为。

## Decisions

1. 手机端拆分“推导顺序”和“展示顺序”

   时间段推导继续按标记时间戳从早到晚进行，以保证相邻标记配对、晚到标记重算边界、开放式当前时间段等行为不变。展示列表在拿到推导后的时间段后，再按开始时间从晚到早排序。

   替代方案是直接反转标记排序后推导时间段，但这会改变相邻标记配对语义，并可能破坏已有标签关联和开放式当前时间段。

2. 手表端以“捕获会话完成”为收尾边界

   每次快捷触发创建并持久化标记后，手表端继续完成必要的定位上下文补充和上报流程；流程完成或进入可后台继续处理的状态后，立即清理本次捕获会话状态，并退出捕获前台状态。若平台提供安全的结束场景/退后台能力，优先使用该能力；若不可用，则通过重置一次性触发状态、短暂成功反馈后关闭捕获界面或返回非捕获根状态，确保下一次双击重新进入捕获流程。

   替代方案是仅依赖前台页面再次触发逻辑，但这无法覆盖“应用已经打开时双击不会重新启动”的系统行为。另一个替代方案是强制 kill/退出应用，这不符合 watchOS 应用生命周期预期，也可能影响定位或同步收尾。

3. 去重范围限定为同一次捕获会话

   现有防重复创建要求仍然保留，但去重 token 或捕获中状态必须在本次捕获完成后释放。这样同一次生命周期重建不会重复创建标记，而下一次明确的快捷触发可以创建新的标记。

## Risks / Trade-offs

- [Risk] 仅调整展示排序可能暴露 UI 中对“第一项是最早时间段”的隐含假设 → Mitigation: 检查时间线列表渲染、标题、滚动定位和开放式当前时间段展示逻辑，确保它们使用明确字段而不是列表索引语义。
- [Risk] 过早结束手表捕获会话可能中断定位补充或同步 → Mitigation: 标记持久化后即可反馈成功；定位和同步若已设计为异步补充，应在会话清理前交给持久化任务或后台可继续执行的路径。
- [Risk] watchOS 不允许应用主动退后台 → Mitigation: 不把退后台作为唯一实现要求，使用关闭捕获界面/回到非捕获状态和释放触发状态作为等价行为。
- [Risk] 清理去重状态过早导致同一次触发生命周期重建重复创建标记 → Mitigation: 只在捕获流程确认完成或失败收尾后释放会话状态，并保留触发内幂等保护。
