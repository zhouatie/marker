## Context

这个变更定义一个新的手表和手机协同流程，用于在一天中快速标记活动边界。当前仓库只有 OpenSpec artifacts，因此实现阶段需要引入应用结构和持久化模型，而不是接入已有代码库。

目标设备是 Samsung Galaxy Watch7 和 Samsung Galaxy S24。手表交互刻意保持最小化：用户将 Watch7 Home 键双击快捷方式配置为打开手表应用，应用记录一个标记事件。手机应用是回顾一天、分配标签和查看辅助位置上下文的主要位置。

## Goals / Non-Goals

**Goals:**

- 通过 Watch7 快捷入口，以最少用户交互捕获一个活动边界标记。
- 在触发时先持久化标记时间戳，然后再等待定位。
- 尽力附加位置元数据，包括可用时的纬度、经度、海拔和精度。
- 将手表创建的标记同步到配对的 S24 手机，并且不丢失离线期间创建的标记。
- 在手机端从相邻标记推导活动时间段。
- 允许用户给时间段分配标签，并主要通过时间线回顾一天。
- 提供地图视图，用直线连接标记点。

**Non-Goals:**

- 连续后台 GPS 追踪。
- 还原标记之间的真实路线。
- 支持 Home 键三连击。
- 手表端标签选择或时间线编辑。
- 在 MVP 中自动推断活动标签。
- 将位置作为该功能的主模型。

## Decisions

### 将标记事件作为时间边界

每次手表快捷触发都创建一个 `MarkerEvent`，而不是直接创建一条活动记录。手机端通过按时间戳排序标记，并将每个标记与下一个标记配对来推导时间段。

理由：用户的主要目标是记住一天中做了什么。一个标记代表“现在开始做一件新事情”；位置只是辅助上下文。

考虑过的替代方案：直接在手表上保存用户创建的活动记录。这会要求用户在手表上选择标签或结束时间，增加快捷流程的操作摩擦。

### 在定位捕获前记录时间戳

手表在应用被快捷方式启动时立即记录 `triggeredAt`。定位捕获随后运行，如果成功则用元数据更新标记。

理由：GPS 获取可能很慢或失败，但活动边界时间必须保持准确。

考虑过的替代方案：等待定位完成后再创建标记。这会让时间戳不准确，并且在位置不可用时有丢失标记的风险。

### 打点成功独立于定位结果

手表端只把“标记事件已创建并持久化”作为快捷打点成功条件。定位捕获在后台尽力补充同一条标记；定位成功、超时或不可用都不应该把已创建的打点覆盖成失败状态。

理由：用户的核心动作是快速记录活动边界。定位只是上下文，不能让 GPS 冷启动、室内信号或权限问题影响打点成功。

考虑过的替代方案：继续把定位结果展示成手表端最终状态。这便于诊断位置问题，但会让用户误以为打点失败，和快捷记录一天活动的目标冲突。

### 手表端位置状态必须可诊断

手表端定位结果必须能解释“位置不可用”的直接原因：如果手表端拿到纬度和经度，系统必须把标记的位置状态更新为成功；如果定位不可用，系统必须在标记状态中区分是权限缺失、系统定位关闭、定位超时，还是定位提供方未返回坐标。

理由：定位状态仍然需要可诊断，方便判断是权限、系统设置还是定位 API 问题；但它不应该覆盖快捷打点本身的成功反馈。

考虑过的替代方案：只保留一个通用“位置不可用”状态。这样无法区分权限、系统设置和定位提供方问题，用户和开发者都无法判断下一步该怎么处理。

### 保持手表反馈以震动为主

手表为标记已接受和记录失败状态提供震动反馈。手表 UI 可以展示短暂状态文本，但不要求用户输入。

理由：这个快捷操作必须在不看手表的情况下仍然可用。

考虑过的替代方案：要求用户在手表上确认。这会提升显式性，但会破坏低摩擦交互。

### 将排队标记从手表同步到手机

手表在本地持久化标记事件及其同步状态。手机通过 Wear OS Data Layer 或等价的配对设备传输方式接收标记事件，并按标记 ID 幂等存储。

理由：用户可能在手机不可用或传输临时断开时创建标记。

考虑过的替代方案：不做本地持久化，直接发送事件。这更简单，但可能丢失用户的活动边界。

### 将手机时间线作为主视图

手机应用将从标记推导出的每日时间线作为主要回顾界面。地图是用于位置上下文的辅助视图。

理由：工作、通勤、带娃等标签描述的是时间段，而不是单个点。

考虑过的替代方案：将地图作为主 UI。这会更偏向位置历史，但会削弱“我今天做了什么”的工作流。

### 时间线按从早到晚展示

手机端每日时间线按时间段开始时间从早到晚、自上而下展示。最新的开放式当前时间段应出现在当天时间线的底部，而不是排在最上方。

理由：这个产品用于回顾“我一天做了什么”，从早到晚符合一天叙事顺序，也能避免最新打点把早上的记录顶下去。

考虑过的替代方案：按最新优先展示。该方式适合消息流，但不适合每日活动回顾。

### 将标签存储在时间段上

时间段标签关联到所选日期中两个相邻标记之间推导出的时间段。

理由：标签描述的是一段时间内进行的活动，而不是捕获标记的那个瞬间。

考虑过的替代方案：将标签存储在标记上。这会产生歧义，因为标记表示下一个时间段的开始。

### 将最新时间段展示为开放式时间段

手机将从最新标记到当前时间的时间段展示为当前开放式时间段，直到另一个标记到达。

理由：用户最新的标记意味着“我现在开始做某件事”；在捕获下一个边界前，应用应该让这个当前活动可见。

考虑过的替代方案：只展示已关闭时间段。这会隐藏当前活动，并让一天中的时间线显得不完整。

## Risks / Trade-offs

- 定位捕获可能失败或不准确 -> 标记仍然会保存准确时间戳和捕获状态，手机时间线仍然可用。
- 手表端位置状态总是不可用 -> 必须优先检查手表端定位权限、系统定位开关、当前定位 provider 选择、超时时间，以及定位 API 是否适合 Wear OS 设备。
- 推导时间段依赖标记排序 -> 标记必须使用稳定 ID 和时间戳；手机必须在晚到标记出现时重新计算受影响时间段。
- 时区和日期边界可能造成困惑 -> 手机应按用户当前本地日期分组用于回顾，同时保留绝对时间戳。
- 离线同步可能产生重复投递 -> 手机必须按稳定标记 ID upsert 标记。
- 地图直线连接可能让用户误以为那是实际经过路径 -> 地图必须将其表达为简单标记连接，而不是还原路线。
- 手表快捷方式配置由用户管理 -> onboarding 必须说明用户需要将 Watch7 Home 键双击配置为打开手表应用。

## Migration Plan

这是一个新能力，没有需要迁移的既有生产数据。

1. 引入手表和手机项目结构。
2. 在两端添加标记事件持久化模型。
3. 实现手表标记捕获和震动反馈。
4. 实现同步传输和手机端幂等接收。
5. 实现手机时间线、时间段标签和地图可视化。
6. 添加配置 Watch7 Home 键双击快捷方式的 onboarding 指引。

回滚时可以移除或隐藏新的手表快捷流程和手机时间线界面，无需迁移既有无关数据。
